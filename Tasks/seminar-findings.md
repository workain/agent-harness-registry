## 1.3 [ПРОВЕРЕНО] s20: `cp -R` без `-P` симлинк НЕ разыменовывает — по крайней мере не там, где это можно проверить

**Место.** s20, строка 39 (`visual`) и строка 45 (речь).

**Что написано сейчас, дословно.**

> «Острый край: `cp -R` без `-P` на macOS разыменовывает симлинк во вторую копию молча —
> копировать через `cp -a` / `git clone` / `git archive`.»

**Чем опровергается.** На GNU coreutils 9.4 это неверно: `cp -R` симлинк сохраняет.
Разыменовывает его только `-L`.

```
$ cp -R  <шаблон> proj-R  && stat -c '%N type=%F' proj-R/AGENTS.md
'proj-R/AGENTS.md' -> 'CLAUDE.md'  type=symbolic link
$ cp -RP <шаблон> proj-RP && stat -c '%N type=%F' proj-RP/AGENTS.md
'proj-RP/AGENTS.md' -> 'CLAUDE.md'  type=symbolic link
$ cp -RH <шаблон> proj-RH && stat -c '%N type=%F' proj-RH/AGENTS.md
'proj-RH/AGENTS.md' -> 'CLAUDE.md'  type=symbolic link
$ cp -a  <шаблон> proj-a  && stat -c '%N type=%F' proj-a/AGENTS.md
'proj-a/AGENTS.md' -> 'CLAUDE.md'  type=symbolic link
$ cp -RL <шаблон> proj-RL && stat -c '%N type=%F' proj-RL/AGENTS.md
'proj-RL/AGENTS.md'  type=regular file
$ cp --version | head -1
cp (GNU coreutils) 9.4
```

**[НЕ ПРОВЕРЕНО]** — именно про macOS. Mac мне недоступен, поэтому утверждение слайда я не
опровергаю для macOS, а говорю, что оно не проверяется там, где можно проверить, и что
формулировка выдаёт за поведение то, что стандарт оставляет неопределённым. Вот это и есть
проверяемая часть — POSIX.1-2024, `cp`, DESCRIPTION (снято 24.09.2026 с
`pubs.opengroup.org/onlinepubs/9799919799/utilities/cp.html`), дословно:

> «If the -R option was specified: If none of the options -H, -L, nor -P were specified, it
> is **unspecified** which of -H, -L, or -P will be used as a default.»

**Готовый текст замены** (строка 39 и соответственно речь):

> 3. `AGENTS.md` — симлинк на тот же файл (`ln -s CLAUDE.md AGENTS.md`). Острый край:
>    поведение `cp -R` на симлинке **стандартом не задано** — POSIX.1-2024 прямо пишет, что
>    при `-R` без `-H`/`-L`/`-P` дефолт не определён. На GNU coreutils симлинк сохраняется,
>    но полагаться на это нельзя; `-P` фиксирует намерение. Гарантированно ломает симлинк
>    `-L` (`cp -RL` даёт вторую настоящую копию, которая потом тихо расходится с первой).

Это утверждение сильнее прежнего, а не слабее: вместо «на macOS бывает так» — «стандарт этого
не обещает, и вот что точно ломает».

## 1.7 [ПРОВЕРЕНО] Кейс 1.3: функции `submitForm()`, на которой держится целевой ответ, в репозитории не существовало

**Место.** `rework/section-1-fayl-instrukciy-part3.md`, строки 40–43 (посылка кейса) и s27
(решение: комментарий к функции).

**Что написано сейчас, дословно.**

> «**Деталь про одну функцию** — `submitForm()` в `src/main.js` при таймауте повторяет
> отправку один раз, поэтому обработчик на стороне сервера обязан быть идемпотентным.»

**Чем опровергалось.** В `src/main.js` не было ни функции `submitForm()`, ни `fetch`, ни
таймаута, ни повтора: форма отправлялась нативным браузерным POST (`action` + `method` в
разметке), а браузер отправку не повторяет.

```
$ git show main:src/main.js | grep -c "submitForm\|fetch\|timeout"
0
$ git show main:index.html | grep -n 'action=\|method='
16:        action="https://formspree.io/f/REPLACE_WITH_YOUR_FORM_ID"
17:        method="POST"
```

То есть посылка кейса не могла быть правдой ни про одну строку этого кода — а вместе с ней и
целевой ответ «деталь уходит комментарием к функции», потому что комментировать было нечего.

**Важная оговорка в пользу семинара.** Сам `rework` называет этот сценарий гипотетическим:
«Новых захватов не требуется — сценарий гипотетический (правдоподобное продолжение

## 4.1 [ПРОВЕРЕНО] Приёмочный критерий требует `ask` там, где правильное поведение — `deny`

**Место.** `10-template-work-order.md`, строки 398 и 404; `-part2.md`, строка 210.

**Дословно.** «прогнать тот же тест на unborn HEAD (пустой репозиторий без коммитов) —
ожидается `ask`, не `deny` и не тихий пропуск»; и в критерии приёмки: «`ask` при unborn HEAD».

**Чем опровергается.** На неродившемся `HEAD` ветка уже известна, поэтому правильный ответ —
`deny`. Воспроизведено:

```
$ git init -b main -q && git symbolic-ref --short HEAD
main                              # ← rc=0, ветка известна
$ git rev-parse --abbrev-ref HEAD
fatal: ambiguous argument 'HEAD': unknown revision…     # rc=128
$ printf '{"tool_input":{"command":"git commit -m x"}}' | bash -c "$HOOK_CMD"
{"…","permissionDecision":"deny","permissionDecisionReason":"BLOCKED: direct commit to
main/master. Create a feature branch first."}
```

Живой хук и его самотест уже **правы**: самотест печатает `PASS  commit on main, unborn HEAD
(no commits yet) — permissionDecision=deny`. Ошибочен только наряд. **Это опаснее обычной
опечатки:** тест, написанный по букве наряда, провалится против правильного хука, и очевидная
«починка» — сломать хук.

**Готовый текст замены.** Везде заменить `ask` на `deny` для unborn HEAD и дописать причину:
«`deny` при unborn HEAD — ветка на неродившемся HEAD уже известна (`git symbolic-ref --short
HEAD` возвращает `main`, код 0), поэтому защита обязана срабатывать; `ask` зарезервирован для
случая, когда репозитория нет вовсе». А случай `ask` описать отдельно: «`ask` когда `git
rev-parse --is-inside-work-tree` не проходит, то есть каталог не репозиторий».

## 4.2 [ПРОВЕРЕНО] Приёмочный критерий требует от самотеста проверки, которой в хуке нет

**Место.** `-part2.md`, строка 210 (тот же абзац).

**Дословно.** «Ожидаемый вывод — построчно: `deny` … при попытке коммита на `main`; `ask`
при unborn HEAD; **`deny` при попытке `rm -rf` с wildcard-паттерном**.»

**Чем опровергается.** Никакой проверки `rm -rf` в хуке нет вовсе, и самотест её не делает:

```
$ grep -c "rm -rf\|wildcard" .claude/settings.json
0
$ grep -n "rm -rf" .claude/hooks/selftest-branch-guard.sh
67:# TMPROOT would turn this line into `rm -rf ""` at best and a much worse mistake at worst.
68:cleanup() { [ -n "$TMPROOT" ] && rm -rf "$TMPROOT"; }
```

Оба вхождения — собственный код уборки скрипта, а не проверка. То есть приёмочный критерий
требует строку вывода, которую хук выдать не может.

**Готовый текст замены.** Убрать третий пункт, либо вынести его в отдельный наряд как
ВТОРОЙ хук с собственным самотестом. Заодно это хороший пример правила из самого шаблона:
каждое новое обязательное правило приезжает со своей механической проверкой в том же
изменении.

## 4.3 [ПРОВЕРЕНО] CVE-2025-59536 приписан механизм, которого в нём нет

**Место.** `10-template-work-order.md`, строки 181, 183, 389; `-part2.md`, строки 215–216.

**Дословно.** «CVE-2025-59536 (CVSS 8.7, RCE через `SessionStart`-хук до диалога доверия к
папке)» и «вредоносный хук на `SessionStart` выполнялся до диалога доверия к папке».

**Чем опровергается.** Это два разных уязвимости из одной публикации Check Point, и механизмы
у них противоположные. По первоисточникам:

```
$ curl -s "https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2025-59536" | …
ID: CVE-2025-59536 | CVSS v4.0: 8.7 HIGH
DESC: "Versions before 1.0.111 were vulnerable to Code Injection due to a bug in the startup
trust dialog implementation. Claude Code could be tricked to execute code contained in a
project BEFORE the user accepted the startup trust dialog."

$ gh api /advisories/GHSA-ph6w-f82w-28w6 --jq '{summary,severity,cve:.cve_id}'
{"cve":null,"severity":"high",
 "summary":"Claude Code Vulnerable to Arbitrary Code Execution Due to Insufficient Startup
 Warning"}
$ gh api /advisories/GHSA-ph6w-f82w-28w6 --jq '.description'
"…This warning did not properly document that selecting 'Yes, proceed' would allow Claude Code
to execute files in the folder without additional confirmation…"
```

То есть: `GHSA-ph6w-f82w-28w6` — хук выполнился **после** принятия диалога доверия, без
